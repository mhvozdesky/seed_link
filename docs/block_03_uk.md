# Block 03 — результат реалізації

## Поведінка

- `analyze_links()` приймає тільки успішний `ImportResult` Block 02 і повертає
  незмінний `AutomaticMatchingResult`. У ньому окремо зберігаються Survey,
  Participant, Activity, LeadRef, Voucher, ProductLine, згадки, зв'язки,
  проблеми та невизначені групи джерельних записів.
- Кілька R1-рядків одного `Survey Response ID` утворюють одне опитування, але
  кожна клітинка `Answer`, `Correct Answer` та `Answer (Long Text)` лишається
  окремим доказом. Рядки без ID опитування не об'єднуються між собою.
- LeadRef з наявним Campaign Member ID об'єднується за цим ID. Без ID однакові
  ПІБ з різних опитувань не об'єднуються. Рядки без ID всередині одного Survey
  можуть використовувати його єдиний явний ID; кілька різних ID створюють
  конфлікт, а не довільний пріоритет.
- Людина зіставляється спочатку за відповідним Campaign Member ID, потім за
  єдиним точним нормалізованим повним ім'ям. Транслітерації, перестановки,
  скорочення, нечіткого або фонетичного пошуку немає. Різні наявні ID, різні
  кандидати імені чи суперечливий email для іменного збігу дають
  `PERSON_LINK_CONFLICT`; тезки — `PERSON_LINK_AMBIGUOUS`; відсутній кандидат —
  `PERSON_LINK_UNRESOLVED`. Розбіжність email не скасовує точний збіг ID, але
  лишається видимою як `PERSON_DATA_MISMATCH`. Для R4 використовується тільки
  `Name`, а Account ID не підміняє ID людини. Ключі Participant та Activity
  включають `snapshot_id`, а 15/18-символьні ID мають спільний ключ.
- R2 індексується один раз за повним нормалізованим номером, парою
  «префікс + увесь цифровий блок» і трійкою «префікс + блок + /N/». Цифри,
  префікси та зміст суфікса не переписуються. Будь-який непорожній номер R2 є
  точним ключем Voucher; ознака «короткий» застосовується лише до згадки R1.
  Тому R2 `SE-123` та `SE-123 ТОВ АГРО` не губляться, а коротка згадка R1
  `SE-123` знаходить обидва через індекс блока. Нерозпізнаний формат R2 також
  зберігається точним значенням із проблемою запису. Усі технічні варіанти
  написання одного нормалізованого номера доступні у `number_variants`, а
  основний `full_number` вибирається детерміновано, не за першим рядком.
- У відповідях шукаються всі згадки незалежно від статусного тексту. Точний
  повний номер приймається один; справді короткий номер приймає всі повні
  ваучери свого префікса й блока; повний `/N/` з іншим дистриб'ютором
  приймається лише за одного кандидата. Суфікс «безкоштовні мішки» є частиною
  повного номера й не відкидається.
- Кілька номерів в одній клітинці утворюють явний набір. Однакові непорожні
  набори різних клітинок підтверджують одне одного. Різні набори, включно з
  відношенням «набір/підмножина», дають `VOUCHER_FIELD_CONFLICT` і не
  приймаються. Незнайдена згадка зберігає `VOUCHER_NOT_FOUND`, але не скасовує
  несуперечливий знайдений набір іншої клітинки. Неоднозначний приблизний збіг
  зупиняє автоматичне прийняття цього Survey.
- `AcceptedLink` унікальний для пари LeadRef–Voucher і не містить кількості.
  Повторні Survey/згадки накопичуються як provenance, а кожна згадка зберігає
  власний метод у `VoucherMatchEvidence`. Тому повтор доказу не множить
  ProductLine або обсяг у наступному блоці.
- Ідентичні дублікати зі стабільним ID дають одну сутність з усіма джерельними
  рядками. Конфліктні та невизначені групи без переможця не перетворюються на
  довільну сутність і передаються через `source_uncertainties` для Block 04.
  Водночас узгоджений повний номер у конфліктних R2-рядках залишається Voucher і
  може бути зіставлений; невизначений внесок ProductLine не підміняється числом.

## Перевірки

`.venv/bin/python -m pytest` покриває ID і точний унікальний ПІБ, тезок,
конфлікти між полями, R4 Name, короткі й повні номери, типографічні дефіси,
повний суфікс безкоштовних мішків, один/кілька `/N/`-кандидатів, явні списки,
повтори доказів, незнайдені номери, конфлікти наборів і підмножин, повторні
рядки Survey, provenance і невизначені дублі.

Локальний integration test на справжніх книгах підтверджує 3 повні прийняті
ваучери, 3 AcceptedLink, 9 учасників і 3 активності. Дві помилкові згадки з
`Correct Answer` залишаються проблемами, а правильні короткі номери з
`Answer (Long Text)` дають усі три ваучери.

## Відомі межі

Block 03 не підсумовує кількості й не обчислює дати, культури, клієнтів,
воронку, «інші ваучери» або query-вибірки. Це робота Block 04. Ручне
підтвердження/відхилення та undo належать Block 05; поточний результат містить
автоматичні кандидати, методи й причини, потрібні для такого перегляду.
