# Block 04 — результат реалізації

## Поведінка

- `build_report_result()` перетворює незмінний результат Block 03 на повний
  `ReportResult` ревізії 0. Ідентифікатор розрахунку детермінований від snapshot
  і ревізії; час розрахунку не бере участі в порівнянні бізнесових фактів.
- Основна множина спочатку визначається за унікальними прийнятими повними
  ваучерами, потім за унікальними `ProductLine`. Повтор LeadRef–Voucher,
  опитування або доказу не множить обсяг. Кількість береться тільки з
  `Current Year Planned Quantity` і лишається `Decimal`.
- `Measure` відрізняє повний результат, відому частину неповного результату та
  недоступний результат. Порожня, некоректна, від'ємна, формульна або
  суперечлива кількість не перетворюється на нуль. Нуль і додатні дробові
  значення є коректними.
- Культура класифікується лише точними погодженими значеннями
  `SUN: Sunflowers` та `CRN: Corn Seeds`; інші непорожні значення і порожня
  культура мають окремі кошики. Гібрид береться тільки з
  `Parent Product Local Description`, а `Local Description` збережено окремим
  атрибутом товарного факту. Розріз гібридів ведеться окремо для кожної
  культури; порожній гібрид має явний кошик, кількість рядків, обсяг і показник
  покриття `main.hybrid.*`.
- Клієнт має ключ `Tax ID 1`. Початкові нулі зберігаються. Рядок без Tax ID не
  втрачає обсяг, але дає `CLIENT_UNKNOWN`. Багатоклієнтський ваучер лишається
  одним ваучером; його власні товарні рядки дають правильні клієнтські частини
  і видиму проблему `MULTIPLE_TAX_IDS`.
- Дата ліда визначається як єдина коректна `Time Taken`, інакше як
  `Member First Associated Date` підтвердженого учасника. Кілька різних
  коректних `Time Taken` дають невизначену дату без fallback. Розбіжність R1/R3
  зберігає пріоритет R1 і створює `DATE_CONFLICT`. ISO timestamp спочатку
  переводиться до календаря `Europe/Kyiv`.
- Для кожної пари лід–ваучер збережено власну часову класифікацію кожного
  ProductLine. Для загального ваучера окремо фіксується найраніша відома дата
  всіх його прийнятих лідів; фільтри її не переобчислюють. Кошики «до»,
  «у день/після» і «невідомо» звіряються з повним обсягом.
- Воронка завжди має базу R3. Активність, змістовна відповідь/Results та
  підтверджений ваучер рахуються незалежними ознаками учасника, тому етапи не
  підганяються під вкладену форму. Окремі `Measure` містять кількості та частки,
  унікальні Survey/Activity, рядки кожного джерела й незв'язані записи.
- «Інші ваучери» допускають Tax ID лише через пов'язаний із основним ваучером
  R3 `Member Type = Lead`. `Contact` сам по собі не допускає клієнта, але не
  скасовує наявний Lead. З усього R2 беруться лише рядки допущеного Tax ID та
  лише ваучери поза глобальною множиною основних. Для клієнта фіксується
  найраніша дата кваліфікуючих Lead і власний часовий розподіл. Цей довідковий
  розділ не збільшує Seed Selector. Клієнт без жодного іншого рядка не створює
  порожній запис розділу; відсутній Tax ID пояснюється `CLIENT_UNKNOWN` і не
  породжує другу шумову проблему допуску.
- Незалежні функції `query_funnel()`, `query_lead_vouchers()`,
  `query_product_lines()`, `query_other_vouchers()` та `query_issues()`
  приймають явні типізовані фільтри. Датний фільтр має окремі режими повного
  набору, діапазону відомих дат і тільки невідомої дати. Підсумки пар
  дедуплікують саме множину ваучерів видимих `AcceptedLink`, навіть якщо
  конфліктний Product ID не створив матеріалізованого ProductLine. Підсумки
  товарів натомість рахуються тільки з видимих ProductLine. Невизначені групи
  R3 консервативно позначають query-вибірку воронки неповною незалежно від
  фільтра: без надійної сутності неможливо довести, що така група не належить
  вибраному типу, стану чи періоду.
- `validate_report_result()` перевіряє контрольні суми культур і часу,
  унікальність товарних внесків, неперетин основних/інших ваучерів, належність
  додаткових рядків допущеним клієнтам і базу воронки. Внутрішньо суперечливий
  результат не повертається як готовий. `ReportInvariantError` містить
  стабільний `CONTROL_TOTAL_MISMATCH` або `INTERNAL_ERROR`, готовий `Issue` і
  діагностичний код; application записує цей код у журнал перед повторним
  підняттям помилки.
- Чисті правила кількостей, культур, гібридів, клієнтів, пар і загальних
  опорних дат живуть у `domain/aggregation.py`. `application/reporting.py`
  лише координує доменні функції та складає фінальний результат, що залишає
  межу для перерахунку Block 05 без нарощування монолітного build-модуля.
- `serialize_report_result()` дає JSON-safe контрольну проєкцію з десятковими
  рядками для Blocks 06–07. `business_control_payload()` відкидає snapshot-bound
  метадані й придатний для перевірки незмінності бізнесового результату при
  іншому порядку джерельних рядків. Це не HTML-проєкція: правила виключення
  контактних даних реалізовуватимуться окремо в Block 07.

## Перевірки

Unit-тести покривають дробові й невідомі кількості, кілька Tax ID, культури,
R1/R3 fallback та конфлікт дат, київську дату біля межі UTC-дня, персональну й
загальну атрибуцію спільного ваучера, незалежні етапи воронки, допуск
Lead/Contact, вибір лише клієнтської частини іншого багатоклієнтського ваучера,
датні/query-фільтри, числову відповідь у воронці, серіалізацію Decimal, а також
Q04, D06 й O03. Перевірка інваріантів окремо доводить наявність стабільного
коду проблеми. Незмінність канонічного результату перевіряється після
перестановки рядків усіх чотирьох ролей.

Локальний integration test справжніх книг підтверджує 3 основні ваучери,
5 товарних рядків, 3 Tax ID, `106 = 19 + 87` і клієнтські частини 7 та 33 у
40-одиничному ваучері. Повний набір тестів не змінює вхідні книги.

## Відомі межі

Ручні рішення, нові ревізії та undo належать Block 05. Block 04 будує ревізію
0 з автоматичних зв'язків Block 03, але його факти й query-контракти вже
придатні для повторного розрахунку після заміни зв'язків. Excel, HTML і desktop
ще не реалізовані; вони мають споживати готовий `ReportResult`, а не повторювати
зіставлення чи часові правила.
